# Участие в разработке impulse

Тот же тон, что у скиллов: коротко, действиями, без маркетингового языка,
без эмодзи, без непроверенных утверждений.

## Добавить скилл

1. Имя директории = имя скилла: `skills/<skill-name>/SKILL.md`, kebab-case.
2. Frontmatter — спецификация agentskills.io, разрешены только эти ключи:
   `name`, `description`, `license`, `allowed-tools`, `metadata`,
   `compatibility`.
   - `name`: ≤64 символов, kebab-case, NFKC-нормализовано, должно точно
     совпадать с именем директории.
   - `description`: ≤1024 символов, без угловых скобок, **только
     триггеры** — описывайте, КОГДА скилл срабатывает, а не пересказ того,
     что он делает. Description, пересказывающий workflow, однажды
     заставил агента следовать пересказу и пропустить обязательный шаг:
     поведением владеет body, роутингом — description
     (`shared/authoring.md`, "Description = triggers only"). Держите
     триггеры напористыми и билингвальными (RU+EN) там, где так делает
     весь остальной сьют.
3. Роутер `SKILL.md` ≤150 строк — жёсткий лимит, проверяет
   `check-skills.js`. Файлы references целятся в ~120 строк: делите по
   домену прежде, чем файл разрастётся так, что не прочитать за один
   присест.
4. Прежде чем писать правило, подберите его форму под тип отказа: запрет
   (называющий конкретную рационализацию) — для отказов "пропущу под
   давлением", позитивный рецепт/шаблон — для отказов формы. Не
   смешивайте: `shared/authoring.md` описывает A/B-результат, где запрет,
   сформулированный против отказа формы, выдал больше нежелательного
   результата, чем вообще никакой инструкции.
5. Кросс-ссылки: `references/x.md` внутри того же скилла, либо
   `skill-name/references/x.md` / `../../skill-name/references/x.md`
   между скиллами — резолвятся обе формы. Голое упоминание `x.md` (без
   слэша) должно совпасть с реальным именем файла где-то в сьюте, иначе
   его нужно добавить в иллюстративный allowlist в `check-skills.js`.

## Внешние источники

Адаптируете паттерн со стороны — пересказывайте его своими словами для
сьюта, никогда не вставляйте отточенный текст правил третьей стороны
дословно, убедитесь, что лицензия источника реально разрешает
редистрибуцию, и добавьте строку в таблицу Lineage в README с указанием,
что именно взято. См. `shared/authoring.md`, "Lineage hygiene."

## Без непроверенных цитат

Утверждение, которое называет что-то конкретное — ID CVE, реальное
поведение библиотеки, число из бенчмарка, реальный инцидент — должно
сводиться к источнику, который вы проверили сами. Не можете проверить?
Пометьте как UNVERIFIED и уберите из отгружаемого контента — не
приклеивайте правдоподобно выглядящую цитату, чтобы правило звучало
авторитетнее, чем есть на самом деле. Собственный research-проход сьюта
уже поймал и исключил две выдуманные цитаты до того, как они попали в
релиз — планка реальная, не декларативная.

## Перед тем как открыть PR

Запустите все три линтера, все три обязаны пройти (это же гейт CI,
`.github/workflows/lint.yml`):

```
node scripts/check-skills.js && node scripts/check-sync.js && node scripts/impulse-debt.js
```

- `check-skills.js` — схема frontmatter, совпадение name/директория,
  лимиты размера, битые ссылки в роутерах, целостность кросс-ссылок между
  файлами references.
- `check-sync.js` — ловит дрейф двух видов. Первый: между компактными
  rulesets в `hooks/impulse-instructions.js` и разделами SKILL.md, которые
  они суммируют. Второй: между правилами билдер-скиллов и тегами
  impulse-review — каждому перечислимому правилу (hard rules фронта,
  baseline и ladder бэка и мобилки, нумерованные правила devops, шаги
  legacy, ошибки security) обязана соответствовать строка в
  `shared/rule-spine.md`, а каждый тег из спайна обязан быть определён в
  impulse-review. Правило без строки в спайне невидимо для ревью, поэтому
  линтер падает. `--verbose` печатает счётчики по доменам. Запускайте после
  правки любой из сторон.
- `impulse-debt.js` — репортит маркеры-потолки `impulse:` по всему
  репозиторию. Маркер без триггера апгрейда — это гниль, а не долг:
  чините его прежде, чем отгружать.

Также обязательно:

- Ни одного пиктографического эмодзи нигде в диффе — ни в коде, ни в
  документации, ни в commit-сообщениях. CI грепает это по всему репозиторию.
- Добавьте запись в `CHANGELOG.md` под текущей версией — это единственный
  журнал проекта.

## Правила дисциплины и evals

Полные eval-кампании — по запросу, не требование на каждый PR
(`shared/evals.md` §4 — гонять всё на каждое изменение — та же
церемония, которую лестница запрещает в коде). Но минимум подгоняйте под
то, что вы затронули:

- Добавили или переформулировали правило, которое модель может пропустить
  под давлением ("просто задеплой", нехватка времени, sunk cost)?
  Прочитайте раздел про wording-test в `shared/authoring.md`; для правила,
  которое реально несёт нагрузку, прогоните один pressure test по
  `shared/evals.md` §3 — убедитесь, что без правила он падает RED, а с
  правилом проходит GREEN.
- Поменяли `description` скилла (роутинг)? Прогоните trigger eval по
  протоколу из `shared/evals.md` §2 — набор запросов с near-miss
  негативами и holdout-сплитом (§2.3).
- Новый скилл? Таблица в `shared/evals.md` §4 даёт минимум: 3 парных
  функциональных eval'а плюс половина набора триггеров.

## Ревью

PR читают по той же лестнице против оверинжиниринга, которой учит сьют
(`skills/impulse-backend/references/ladder.md`) — новый скилл или правило
зарабатывает свою строчку так же, как новая абстракция зарабатывает
строчку в коде.
